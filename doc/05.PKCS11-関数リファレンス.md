## 命名規則（これだけ覚えれば読める）

PKCS#11 の関数は **すべて `C_` で始まり**、処理系は **3 段ロケット**で命名される。

| 接尾辞 | 意味 | 例 |
|---|---|---|
| `...Init` | 操作の開始。メカニズムと鍵を指定 | `C_SignInit` |
| （無印） | 一発で完了（小さいデータ向け） | `C_Sign` |
| `...Update` | データを少しずつ投入（大きいデータ向け） | `C_SignUpdate` |
| `...Final` | 分割投入の締め。結果を取り出す | `C_SignFinal` |

cryptoki は `Init` + 無印を **1 メソッドに合体**して隠す（例: `C_SignInit`+`C_Sign` → `session.sign()`）。

## 「一発」と「分割」の違い（ここが分かれば全部読める）

署名・暗号化・ハッシュなどの処理には、**同じことをやる2つのやり方**がある。
結果は全く同じで、**データの渡し方だけが違う**。

### たとえ：荷物をトラックで運ぶ

- **一発(one-shot)** = 荷物を**全部まとめて1回で**積んで運ぶ。
  データがメモリに収まる普通のサイズなら、これでよい。一番簡単。
- **分割(multi-part / ストリーム)** = 荷物が大きすぎて1回で積めないとき、
  **何回かに分けて**積み込み、最後に「もう全部積んだ、出発」と合図する。

つまり「分割」とは “処理を分けて違うことをする” ではなく、
**“1つの処理に、データを何回かに分けて流し込む”** という意味。

### 具体的に並べると

| | 一発 | 分割 |
|---|---|---|
| 呼ぶ回数 | 1 回 | 開始 1 + 投入 N + 締め 1 |
| C API | `C_Sign` | `C_SignInit` → `C_SignUpdate`×N → `C_SignFinal` |
| cryptoki | `session.sign(...)` | `sign_init()` → `sign_update()`×N → `sign_final()` |
| 向いている場面 | 小さいデータ（メッセージ等） | 巨大データ（GB 級のファイル等。全部メモリに載せたくない） |
| 結果 | **完全に同じ** | **完全に同じ** |

### コードで見る（同じ署名を2通りで）

```rust
// 【一発】データ全部を1回で渡す
let sig = session.sign(&mech, key, b"hello world")?;

// 【分割】同じ署名を、データを小分けにして渡す
session.sign_init(&mech, key)?;     // ① 開始（メカニズムと鍵をセット）
session.sign_update(b"hello ")?;    // ② データ前半を投入
session.sign_update(b"world")?;     // ②' データ後半を投入（何回でもOK）
let sig = session.sign_final()?;    // ③ 締めて署名を受け取る
```

- **分割復号** = 暗号文を小分けに `decrypt_update()` で流し込み、`decrypt_final()` で締める復号。
- **分割ハッシュ** = データを小分けに `digest_update()` で流し込み、`digest_final()` でハッシュを得る。
  （`ops/stream.rs` ではわざと 16 バイトずつに区切って、この仕組みを見せている）

> 迷ったら **一発**でよい。「分割」は “巨大データをメモリに全部載せずに処理したい” ときの上級テク。

## cryptoki の引数の読み方（`session.sign(&mech, key, data)` など）

処理系メソッドの引数は、だいたい **「①手順」「②鍵」「③データ」** の3点セット。
これは「金庫の窓口に出す注文書」と同じ構成。

### `session.sign(&mech, key, data)` を分解

```rust
let signature = session.sign(&mech, key, data)?;
//                            ▲     ▲    ▲
//                            │     │    └ data : 署名したいデータ(&[u8] = バイト列)
//                            │     └────── key  : どの鍵で署名するか(鍵のハンドル=整理番号)
//                            └──────────── mech : どの手順(アルゴリズム)で署名するか
```

| 引数 | 型 | 意味 | たとえ |
|---|---|---|---|
| `&mech` | `&Mechanism` | アルゴリズム指定（例 `Mechanism::Sha256RsaPkcs` = SHA256でハッシュしてRSA署名） | 注文書の「作業手順」欄 |
| `key` | `ObjectHandle` | **鍵そのものではなく整理番号**。`find_key()` や `generate_*()` が返す。HSM はこの番号で金庫内の鍵を特定する（鍵の中身はアプリに渡らない） | 「金庫内の何番の鍵を使え」 |
| `data` | `&[u8]` | 処理対象のバイト列。文字列なら `"hello".as_bytes()` で変換 | 「これを処理して」 |
| 戻り値 | `Result<Vec<u8>>` | 成功すれば署名バイト列。失敗は `Err`（`?` で伝播） | 窓口から返る「結果」 |

### 他のメソッドも同じ並び

| メソッド | ①手順 | ②鍵 | ③データ | 戻り値 |
|---|---|---|---|---|
| `session.sign(&mech, key, data)` | `&mech` | 秘密鍵ハンドル | 署名対象 | 署名 `Vec<u8>` |
| `session.verify(&mech, key, data, sig)` | `&mech` | 公開鍵ハンドル | 元データ | `()`（OK/NG） |
| `session.encrypt(&mech, key, data)` | `&mech` | 鍵ハンドル | 平文 | 暗号文 `Vec<u8>` |
| `session.decrypt(&mech, key, data)` | `&mech` | 鍵ハンドル | 暗号文 | 平文 `Vec<u8>` |
| `session.digest(&mech, data)` | `&mech` | （鍵不要） | 対象 | ハッシュ `Vec<u8>` |

> ポイント: **②の `key` は鍵の実体ではなく「ハンドル(整理番号)」**。
> これが「秘密鍵は金庫から出さず、番号で指定して処理だけ頼む」という HSM の核心。
> `&` は Rust の「借用（値をコピーせず参照だけ渡す）」の印で、PKCS#11 の意味とは無関係。

## 残り（◯/✕）を足すなら

- **◯ 未配線**（cryptoki にラッパーあり、`ops/` に関数を足すだけ）:
  `C_CreateObject` / `C_SetAttributeValue` / `C_Encrypt|DecryptUpdate/Final` /
  `C_DigestKey` / `C_WaitForSlotEvent`
- **✕ ラッパー無し**（生 FFI で `src/main.rs` 方式が必要）:
  `C_*Recover*` / `C_Get|SetOperationState` / 複合操作 4 種 /
  `C_GetFunctionStatus` / `C_CancelFunction` / `C_GetObjectSize` / `C_CloseAllSessions`
