# 04. cryptoki セットプログラム解説

`cryptoki` クレートで HSM(SoftHSM2 など)を操作する「機能別セットプログラム」の解説。
**概念 → コードの地図 → 使い方** の順で読めば、`src/` のどのファイルが何をしているか分かるようになる。

> 既存の `src/main.rs` は「生 FFI で C API を手で叩く学習用」。
> こちらは「`cryptoki` クレートで実用的に書く版」。狙いが違う2本立て。

---

## 1. まず概念（金庫のたとえ）

| 概念 | たとえ | 意味 |
|---|---|---|
| Library(.so) | 業務マニュアル | `libsofthsm2.so`。これをロードして全関数を得る |
| Slot | 金庫の差込口 | 接続点。スロット番号で指定 |
| Token | 金庫本体 | 鍵やデータの実体。HSM 本体 |
| Session | 面談中の状態 | Token と会話する接続。開く→使う→閉じる |
| Login | 暗証番号で本人確認 | PIN を入れる。秘密鍵操作にはほぼ必須 |
| Object | 金庫の中身 | 鍵・証明書・データ。各々に Handle(整理番号)が付く |
| Attribute | 中身に貼るラベル | `Sign=true`(署名可), `Extractable=false`(持出禁止) など |
| Mechanism | 作業手順 | `RsaPkcs`, `Ecdsa`, `AesCbcPad` などアルゴリズム指定 |

**最重要原則**: 秘密鍵は金庫から出ない。アプリは「これに署名して」と注文書
(Mechanism + データ + 鍵Handle)を渡し、**結果だけ**受け取る。

---

## 2. 会話の骨格（ライフサイクル）と 3 段ロケット

### 外枠（ライフサイクル）
```
connect()      … C_GetFunctionList + C_Initialize
  pick_slot()    … C_GetSlotList
    login_rw()     … C_OpenSession + C_Login
      ── 本番処理 ──
    (自動)         … C_Logout / C_CloseSession  ← Session の Drop で自動
  (自動)         … C_Finalize                   ← Pkcs11 の Drop で自動
```
cryptoki は終了処理(`Finalize`/`CloseSession`/`Logout`)を **Drop で自動化**するので、
自分で書くのは「接続〜ログイン〜本番処理」だけ。

### 中身（3 段ロケット）
PKCS#11 の処理系は **Init → 本体 → (Final)** で統一。cryptoki は前 2 段を 1 メソッドに合体する。

| 操作 | C API | cryptoki |
|---|---|---|
| 署名 | `C_SignInit` + `C_Sign` | `session.sign(...)` |
| 検証 | `C_VerifyInit` + `C_Verify` | `session.verify(...)` |
| 暗号化 | `C_EncryptInit` + `C_Encrypt` | `session.encrypt(...)` |
| 復号 | `C_DecryptInit` + `C_Decrypt` | `session.decrypt(...)` |
| 検索 | `C_FindObjectsInit` + `Find` + `Final` | `session.find_objects(...)` |

## 3. C API ↔ cryptoki 対応表

| C API | cryptoki | 隠され方 |
|---|---|---|
| `C_GetFunctionList`+`C_Initialize` | `Pkcs11::new()` + `.initialize(CInitializeArgs::OsThreads)` | 関数表取得は内部で自動 |
| `C_Finalize` | `Pkcs11` の Drop | 書かなくてよい |
| `C_GetInfo` | `pkcs11.get_library_info()` | バージョン/ベンダー |
| `C_GetSlotList` | `pkcs11.get_slots_with_token()` | `Vec<Slot>` |
| `C_GetSlotInfo`/`C_GetTokenInfo` | `get_slot_info()` / `get_token_info()` | 構造体で返る |
| `C_GetMechanismList` | `pkcs11.get_mechanism_list(slot)` | 対応アルゴリズム一覧 |
| `C_OpenSession` | `pkcs11.open_rw_session(slot)` | RO/RW をメソッド名で表現 |
| `C_Login`/`C_Logout` | `session.login(UserType::User, Some(&pin))` / Drop | ユーザ種別が enum |
| `C_GenerateKeyPair` | `session.generate_key_pair(&mech, &pub_t, &priv_t)` | 属性が `Vec<Attribute>` |
| `C_GenerateKey` | `session.generate_key(&mech, &t)` | 対称鍵用 |
| `CK_RV`(0=OK) | `Result<T, Error>` | `0` 判定が `?` に |
| `CK_ATTRIBUTE` | `Attribute::Sign(true)` などの enum | byte 詰め不要・型安全 |
| `CK_MECHANISM` | `Mechanism::RsaPkcsKeyPairGen` などの enum | 同上 |

### `CInitializeArgs` の意味
`C_Initialize` の引数は暗号と無関係で「マルチスレッド時のロック方法」だけを決める。
C 仕様では 4 モードあるが、cryptoki(0.10) は実用上唯一の選択肢
**`OsThreads`（= `CKF_OS_LOCKING_OK`、OS ネイティブロックでスレッドセーフ）** だけを公開している。

### 「バージョン」は 4 種類ある
```
get_library_info() → cryptoki_version  // ① 仕様(API)の版  例 2.40 / 3.2
                   → library_version   // ② ライブラリ実装の版
get_slot_info()    → hardware_version  // ③ ハード版
                   → firmware_version  // ④ ファーム版
```

## 4. ファイル構成（どれが何をするか）

```
src/
├── lib.rs            共通の Result 型 + モジュール宣言
├── session.rs        接続・スロット選択・ログイン・鍵検索（会話の骨格）
├── ops/
│   ├── mod.rs
│   ├── info.rs       Utility 系: バージョン/スロット/メカニズム取得
│   ├── keygen.rs     鍵生成: RSA / EC / AES
│   ├── sign.rs       署名 / 検証
│   └── crypt.rs      暗号化 / 復号
└── bin/
    └── hsm.rs        CLI 本体（サブコマンドで上記を呼び分け）
```

**「署名したい → `ops/sign.rs`」「RSA 生成 → `ops/keygen.rs::rsa`」「取得系 → `ops/info.rs`」**
という対応で目的のコードにすぐ飛べる。

### 鍵生成 3 種の比較（`ops/keygen.rs`）
| 鍵 | 関数 | メソッド | Mechanism | 鍵長/曲線の指定 |
|---|---|---|---|---|
| RSA | `keygen::rsa` | `generate_key_pair` | `RsaPkcsKeyPairGen` | `ModulusBits(2048)` + `PublicExponent` |
| EC | `keygen::ec` | `generate_key_pair` | `EccKeyPairGen` | `EcParams(OIDのDER)` |
| AES | `keygen::aes` | `generate_key`(単数) | `AesKeyGen` | `ValueLen(32)` |

非対称＝ペア生成(テンプレ2つ)、対称＝単数生成(テンプレ1つ)。

## 5. 使い方

### 準備（SoftHSM2 でトークン初期化）
```bash
softhsm2-util --init-token --slot 0 --label "test" --so-pin 1234 --pin 1234
# .so を lib/ に置く（または環境変数 PKCS11_LIB で指定）
```

### 実行
```bash
# 取得系（ログイン不要・最初の疎通確認に最適）
cargo run --bin hsm -- info

# 鍵生成
cargo run --bin hsm -- gen-rsa 2048 mykey
cargo run --bin hsm -- gen-ec  myec
cargo run --bin hsm -- gen-aes 32 myaes

# 署名 → 検証（sign が出す sig-hex を verify に渡す）
cargo run --bin hsm -- sign   mykey "hello hsm"
cargo run --bin hsm -- verify mykey "hello hsm" <sig-hex>

# 暗号化 → 復号
cargo run --bin hsm -- encrypt myaes "secret"
cargo run --bin hsm -- decrypt myaes <ct-hex>
```

### 設定（環境変数）
| 変数 | 既定 | 意味 |
|---|---|---|
| `PKCS11_LIB` | `lib/libsofthsm2.so` | .so のパス |
| `PKCS11_PIN` | `1234` | ユーザ PIN |
| `PKCS11_SLOT` | `0` | スロット index |

実機 HSM へ移すときは、基本この 3 つ（パス・PIN・スロット）を変えるだけ。
PKCS#11 標準のおかげでコードはほぼそのまま動く（ベンダー独自メカニズムの有無だけ注意）。

---

## 6. 学習ステップ（おすすめ順）
1. `info`（ログイン不要・3段ロケット無し。一番簡単）
2. `gen-rsa` → `sign` → `verify`（PKCS#11 の中核）
3. `gen-aes` → `encrypt` → `decrypt`
4. `ops/*.rs` を読んで C API 対応表(§3)と突き合わせる
5. 実機 HSM へ（.so/PIN/スロットの差し替えのみ）
