# 07. ユーザ認証と情報取得の詳解

このドキュメントは2本立て:
- **Part A** … ユーザ・ログイン・PIN・セッション状態（「誰が・どの状態で・何をできるか」）
- **Part B** … 情報取得系（ライブラリ/スロット/トークン/セッション/メカニズムの各フィールドの意味）

金庫のたとえ: トークン=金庫、PIN=暗証番号、セッション=面談、ログイン=本人確認。

---

# Part A. ユーザと認証

## A-1. 2人の登場人物：User と SO

PKCS#11 のログインには **役割(UserType)** が2つ（＋特殊な1つ）。

| 役割 | cryptoki | 何をする人か | できること |
|---|---|---|---|
| **User** | `UserType::User` | 日常の利用者 | 鍵で署名/暗号/復号、鍵生成、private オブジェクトの読み書き |
| **SO** (Security Officer) | `UserType::So` | 管理者 | トークン初期化、**User PIN の初期設定**。鍵での暗号操作は**できない** |
| Context-Specific | `UserType::ContextSpecific` | 特殊 | `AlwaysAuthenticate` な鍵を使う直前の再認証など |

> 重要: **SO は「鍵を使う人」ではなく「User の面倒をみる管理者」**。
> SO でログインしても、ユーザの秘密鍵で署名したりはできない。

```rust
session.login(UserType::User, Some(&AuthPin::new("1234".into())))?; // 利用者として
session.login(UserType::So,   Some(&AuthPin::new("0000".into())))?; // 管理者として
```

## A-2. public オブジェクト と private オブジェクト

オブジェクトには「ログイン不要で見えるもの」と「User ログインが要るもの」がある。
これを決めるのが鍵生成時の **`Private` 属性**。

| | `Private(false)` = public | `Private(true)` = private |
|---|---|---|
| 例 | 公開鍵、公開証明書 | 秘密鍵、共通鍵 |
| 見るのに | ログイン不要 | **User ログインが必要** |

だから「`info` は動くのに、鍵を使う操作はログインしないと失敗する」のはこのため。
（本プログラムの `session.rs::login_rw` が `C_Login` を呼んでいる）

## A-3. PIN のライフサイクル（誰がいつ設定するか）

```
SO が C_InitToken     → トークンを初期化し SO-PIN を決める（中身は全消去）
SO が C_Login(SO)     → 管理者としてログイン
SO が C_InitPIN       → User PIN を初期設定する          ← User PIN はここで誕生
User が C_Login(User) → 以後、利用者として鍵を使える
User/SO が C_SetPIN   → 自分の PIN を変更する
```

対応コマンド（`src/ops/admin.rs`）:
```bash
cargo run --bin hsm -- init-token <so-pin> <label>   # ⚠️全消去
cargo run --bin hsm -- init-pin   <new-user-pin>     # SO ログイン下で
cargo run --bin hsm -- set-pin    <old> <new>        # PIN 変更
```

> SoftHSM では `softhsm2-util --init-token ... --so-pin ... --pin ...` で
> 上の InitToken+InitPIN をまとめてやってくれる。

## A-4. PIN の状態フラグ（ロックや要変更を知る）

`C_GetTokenInfo`(= `get_token_info`) は PIN の健康状態も返す。`info` でも一部表示。

| TokenInfo ゲッター | 意味 |
|---|---|
| `user_pin_initialized()` | User PIN が設定済みか |
| `user_pin_locked()` | 連続失敗で**ロック**されたか |
| `user_pin_final_try()` | あと1回失敗でロックの崖っぷちか |
| `user_pin_count_low()` | 失敗回数が増えてきているか |
| `user_pin_to_be_changed()` | 次回ログイン時に変更が必要か |
| `so_pin_*()` | 上記の SO 版 |
| `login_required()` | そもそもログインが要るトークンか |
| `protected_authentication_path()` | PIN をPINパッド等から入れる方式か（アプリが PIN を渡さない） |

> `user_pin_locked()` が true なら、いくら正しい PIN でも `C_Login` は失敗する。
> SO が再設定するまで使えない。デバッグ時に「PIN 合ってるのに入れない」原因はこれが多い。

## A-5. ログイン状態は「アプリ単位」で共有される（要注意の仕様）

PKCS#11 の独特な点: **ログイン状態は1つのセッションではなく、
そのアプリがそのトークンに対して開いている全セッションで共有**される。

- どれか1つのセッションで User ログインすると、同じトークンの**他のセッションもログイン状態**になる。
- どれか1つで `C_Logout` すると、**全部ログアウト**になる。
- cryptoki では `Session` を drop すると自動 logout/close されるので、
  ログイン中の鍵操作はその `Session` が生きている間に済ませる。

# Part B. 情報取得の詳解

情報は **5階層**。上から下へ「ライブラリ → スロット → トークン → セッション → メカニズム」。

```
get_library_info()         ライブラリ全体     (C_GetInfo)
 └ get_slot_info(slot)      差込口            (C_GetSlotInfo)
    └ get_token_info(slot)  金庫本体          (C_GetTokenInfo)
       └ session.get_session_info()  面談状態 (C_GetSessionInfo)
get_mechanism_list/info()   対応アルゴリズム  (C_GetMechanismList/Info)
```

## B-1. ライブラリ情報（C_GetInfo / `Info`）

| ゲッター | 意味 |
|---|---|
| `cryptoki_version()` | **仕様(API)** のバージョン（例 2.40 / 3.2） |
| `library_version()` | **実装** のバージョン（例 SoftHSM 2.6） |
| `manufacturer_id()` | ライブラリのベンダー名 |
| `library_description()` | ライブラリの説明文字列 |

> バージョンは「仕様」と「実装」で別物。詳しくは doc/05 の §バージョン参照。

## B-2. スロット情報（C_GetSlotInfo / `SlotInfo`）

| ゲッター | 意味 |
|---|---|
| `slot_description()` | スロット(差込口)の説明 |
| `manufacturer_id()` | スロットのベンダー |
| `hardware_version()` / `firmware_version()` | スロット側の HW/FW バージョン |
| `token_present()` | トークンが刺さっているか |
| `removable_device()` | 抜き差しできるデバイスか（スマートカード等） |
| `hardware_slot()` | 物理スロットか（論理スロットでないか） |

## B-3. トークン情報（C_GetTokenInfo / `TokenInfo`）— 一番情報が多い

グループで捉えると読みやすい。

### (a) 識別
`label()` / `model()` / `manufacturer_id()` / `serial_number()`

### (b) 状態
| ゲッター | 意味 |
|---|---|
| `token_initialized()` | 初期化済みか |
| `write_protected()` | 書込禁止か（新規オブジェクトを作れない） |
| `login_required()` | ログインが要るか |
| `rng()` | 乱数生成器を持つか（`gen-random` が使えるか） |
| `clock_on_token()` | 時計を内蔵するか |
| `dual_crypto_operations()` | 複合操作(C_*Update系)に対応するか |

### (c) 容量・規模
| ゲッター | 意味 |
|---|---|
| `total_public_memory()` / `free_public_memory()` | public 領域のメモリ（`Option`：不明なら `None`） |
| `total_private_memory()` / `free_private_memory()` | private 領域のメモリ |
| `max_session_count()` / `session_count()` | セッション数の上限/現在 |
| `max_rw_session_count()` / `rw_session_count()` | RW セッションの上限/現在 |
| `min_pin_length()` / `max_pin_length()` | PIN 長の下限/上限 |

> `Option`/`Limit` 型なのは、PKCS#11 が「不明」「無制限」という値を持つから。
> `None` は「この値は取れない/不明」の意味。

### (d) PIN 状態
A-4 の表（`user_pin_*` / `so_pin_*`）がここに含まれる。

本プログラムの `info` は (a)(b)(c) と User PIN 状態を抜粋表示する:
```bash
cargo run --bin hsm -- info
```

## B-4. セッション情報（C_GetSessionInfo / `SessionInfo`）

| ゲッター | 意味 |
|---|---|
| `slot_id()` | このセッションが属するスロット |
| `read_write()` | RW セッションか（false なら RO） |
| `session_state()` | **下の5状態**のどれか |
| `device_error()` | 直近のデバイスエラーコード |

```bash
cargo run --bin hsm -- session-info
```

### セッションの5状態（状態機械）

セッションは「RO/RW」×「誰でログイン中か」で状態が決まる。

| 状態 (`SessionState`) | RO/RW | ログイン | 見える物 / できる事 |
|---|---|---|---|
| `RoPublic` | RO | 無し | public のみ・読み取り中心 |
| `RoUser` | RO | User | private も見える・**token(永続)オブジェクトの作成は不可** |
| `RwPublic` | RW | 無し | public の作成・変更可 |
| `RwUser` | RW | User | **フル機能**（鍵生成・署名・private 永続オブジェクト作成）|
| `RwSecurityOfficer` | RW | SO | 管理操作（InitPIN 等）。鍵での暗号操作は不可 |

ポイント:
- **RO セッションでは「token(永続)オブジェクト」を新規作成できない**。鍵生成は RW が要る
  → だから本プログラムは `open_rw_session` を使っている。
- **SO は RW でしかログインできない**（`RwSecurityOfficer` はあるが RO 版は無い）。
- User ログインすると `RoPublic→RoUser` / `RwPublic→RwUser` に遷移、logout で戻る。

```
            login(User)              login(User)
 RoPublic ───────────────► RoUser   RwPublic ──────────► RwUser
    ▲          logout         │         ▲      logout       │
    └──────────────────────────         └──────────────────┘
 RwPublic ── login(SO) ──► RwSecurityOfficer
```

## B-5. メカニズム情報（C_GetMechanismList/Info / `MechanismInfo`）

- `get_mechanism_list(slot)` … トークンが対応する**アルゴリズム一覧**
- `get_mechanism_info(slot, ty)` … 各アルゴリズムの詳細

| MechanismInfo ゲッター | 意味 |
|---|---|
| `min_key_size()` / `max_key_size()` | 使える鍵長の下限/上限 |
| `sign()` / `verify()` / `encrypt()` / `decrypt()` / `digest()` | その用途に使えるか |
| `generate_key_pair()` / `generate()` | 鍵(ペア)生成に使えるか |
| `wrap()` / `unwrap()` / `derive()` | ラップ/アンラップ/導出に使えるか |
| `hardware()` | ハードウェアで処理されるか |

実機 HSM 評価では「**RSA-4096 を本当にサポートするか**」等をここで確認:
```bash
cargo run --bin hsm -- mech-info RsaPkcsKeyPairGen
```

---

## まとめ：認証と情報の関係
- まず `info`（ログイン不要）で**繋がるか・対応機能・PIN 状態**を確認する。
- private な鍵を触るには **User ログイン**（`Private(true)` のため）。
- 永続鍵を作るには **RW セッション**（RO では token オブジェクト作成不可）。
- 管理(PIN設定)は **SO ＋ RW**。
- 困ったら `session-info` で今の状態(`RwUser` 等)を確認し、想定の状態かを照合する。
