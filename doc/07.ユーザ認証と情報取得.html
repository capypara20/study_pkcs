    PART A · 認証

    A-12人の登場人物：User と SO

    役割cryptoki何をする人かできること
    UserUserType::User日常の利用者署名/暗号/復号, 鍵生成, private 読み書き
    SOUserType::So管理者(Security Officer)トークン初期化, User PIN 初期設定。暗号操作は不可
    Context-SpecificUserType::ContextSpecific特殊AlwaysAuthenticate な鍵の直前再認証など

    SO は「鍵を使う人」ではなく「User の面倒をみる管理者」。SO でログインしても、ユーザの秘密鍵で署名したりはできない。

    rust
    session.login(UserType::User, Some(&AuthPin::new("1234".into())))?; // 利用者として
session.login(UserType::So,   Some(&AuthPin::new("5678".into())))?; // 管理者として

    PART A · 認証

    A-2public と private オブジェクト

    オブジェクトには「ログイン不要で見えるもの」と「User ログインが要るもの」がある。これを決めるのが鍵生成時の Private 属性。

    Private(false) = publicPrivate(true) = private
    例公開鍵、公開証明書秘密鍵、共通鍵
    見るのにログイン不要User ログインが必要

    「info は動くのに、鍵を使う操作はログインしないと失敗する」のはこのため。（session.rs::login_rw が C_Login を呼ぶ）

    PART A · 認証

    A-3/4PIN のライフサイクルと状態フラグ

    pin lifecycle
    SO が C_InitToken     → トークン初期化し SO-PIN を決める（中身は全消去）
SO が C_Login(SO)     → 管理者としてログイン
SO が C_InitPIN       → User PIN を初期設定する          ← User PIN はここで誕生
User が C_Login(User) → 以後、利用者として鍵を使える
User/SO が C_SetPIN   → 自分の PIN を変更する
    shell
    cargo run --bin hsm -- init-token <so-pin> <label>   # ⚠️全消去
cargo run --bin hsm -- init-pin   <new-user-pin>     # SO ログイン下で
cargo run --bin hsm -- set-pin    <old> <new>        # PIN 変更

    SoftHSM では softhsm2-util --init-token --free --label test --so-pin 5678 --pin 1234 で InitToken+InitPIN をまとめて実行できる。

    TokenInfo ゲッター意味
    user_pin_initialized()User PIN が設定済みか
    user_pin_locked()連続失敗でロックされたか
    user_pin_final_try() / user_pin_count_low()あと1回でロック / 失敗が増えてきた
    user_pin_to_be_changed()次回ログイン時に変更が必要か
    so_pin_*()上記の SO 版
    login_required() / protected_authentication_path()ログインが要るか / PINパッド方式か

    user_pin_locked() が true なら、正しい PIN でも C_Login は失敗。SO が再設定するまで使えない。「PIN 合ってるのに入れない」原因はこれが多い。

    PART A · 認証

    A-5ログイン状態は「アプリ単位」で共有される

    PKCS#11 の独特な点: ログイン状態は1つのセッションではなく、そのアプリがそのトークンに対して開いている全セッションで共有される。

    • どれか1つのセッションで User ログインすると、同じトークンの他のセッションもログイン状態になる。
    • どれか1つで C_Logout すると、全部ログアウトになる。
    • cryptoki では Session を drop すると自動 logout/close されるので、ログイン中の鍵操作はその Session が生きている間に済ませる。

    B-3トークン情報（一番情報が多い）

    (a) 識別: label() / model() / manufacturer_id() / serial_number()

    (b) 状態

    B-4RO と RW の違い

    セッションを開くとき最初に決めるのが RO(Read-Only) か RW(Read-Write) か。「トークンに永続的な変更を加えられるか」の違い。ログイン(User/SO)とは別の軸。

    操作RORW
    既存鍵で署名/検証/暗号/復号✅✅
    乱数生成・ハッシュ・検索・属性読み取り✅✅
    User ログイン✅✅
    SO ログイン❌✅
    Token(true) 鍵の生成・作成❌✅
    オブジェクトの削除・属性変更❌✅
    PIN 変更・InitPIN❌✅

    RO でできないのは「永続オブジェクトをいじること」と「SO ログイン」だけ。鍵を“使う”操作は RO でも全部できる。本プログラムは鍵生成までやるので open_rw_session を使う。

    RO で gen-rsa 等をやると CKR_SESSION_READ_ONLY で弾かれる。「鍵が作れない」ときはまずセッション種別を疑う。

    B-5セッションの5状態（状態機械）

    状態 (SessionState)RO/RWログインできる事
    RoPublicRO無しpublic のみ・読み取り中心
    RoUserROUserprivate も見える・token(永続)作成は不可
    RwPublicRW無しpublic の作成・変更可
    RwUserRWUserフル機能（鍵生成・署名・private 永続作成）
    RwSecurityOfficerRWSO管理操作（InitPIN 等）。暗号操作は不可
    state machine
                login(User)              login(User)
 RoPublic ───────────────► RoUser   RwPublic ──────────► RwUser
    ▲          logout         │         ▲      logout       │
    └──────────────────────────         └──────────────────┘
 RwPublic ── login(SO) ──► RwSecurityOfficer

    cargo run --bin hsm -- session-info で今の状態(RwUser 等)を確認できる。SO は RW でしかログインできない。

    CLOSING

    まとめ：認証と情報の関係

    • まず info（ログイン不要）で繋がるか・対応機能・PIN 状態を確認する。
    • private な鍵を触るには User ログイン（Private(true) のため）。
    • 永続鍵を作るには RW セッション（RO では token オブジェクト作成不可）。
    • 管理(PIN設定)は SO ＋ RW。
    • 困ったら session-info で今の状態(RwUser 等)を確認し、想定と照合する。
