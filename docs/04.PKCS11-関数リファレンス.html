    PKCS#11 関数リファレンス

    公式仕様（OASIS PKCS#11）は英語で量も多く読みにくいので、全関数を日本語1行で整理した早見表。 本体の表 A〜J は example_fnList.txt（SoftHSM2 が公開する PKCS#11 2.40 の 68 関数）に対応する。 末尾の §K に 3.0／3.2 で追加された関数（メッセージAPI・KEM・新検証系・インターフェース系）をまとめた。

    現行の最新仕様は v3.2（OASIS CS01, 2025-11-14）で、関数総数は概算で 2.40: 68 ＋ 3.0: +24 ＋ 3.2: +6 ≒ 98。 本プログラム（cryptoki 0.10）が主に扱うのは 2.40 の範囲。

    命名規則（これだけ覚えれば読める）

    PKCS#11 の関数は すべて C_ で始まり、処理系は 3 段ロケットで命名される。

    接尾辞意味例
    ...Init操作の開始。メカニズムと鍵を指定C_SignInit
    （無印）一発で完了（小さいデータ向け）C_Sign
    ...Updateデータを少しずつ投入（大きいデータ向け）C_SignUpdate
    ...Final分割投入の締め。結果を取り出すC_SignFinal

    cryptoki は Init + 無印を 1 メソッドに合体して隠す（例: C_SignInit+C_Sign → session.sign()）。

    「一発」と「分割」の違い

    署名・暗号化・ハッシュなどの処理には、同じことをやる2つのやり方がある。結果は全く同じで、データの渡し方だけが違う。

    • 一発(one-shot) = 荷物を全部まとめて1回で積んで運ぶ。メモリに収まる普通のサイズならこれでよい。
    • 分割(multi-part / ストリーム) = 大きすぎて1回で積めないとき、何回かに分けて積み込み、最後に「もう全部積んだ、出発」と合図する。

    つまり「分割」とは “処理を分けて違うことをする” ではなく、“1つの処理に、データを何回かに分けて流し込む” という意味。

    一発分割
    呼ぶ回数1 回開始 1 + 投入 N + 締め 1
    C APIC_SignC_SignInit → C_SignUpdate×N → C_SignFinal
    cryptokisession.sign(...)sign_init() → sign_update()×N → sign_final()
    向いている場面小さいデータ巨大データ（GB 級。全部メモリに載せたくない）
    結果完全に同じ完全に同じ
    rust
    // 【一発】データ全部を1回で渡す
let sig = session.sign(&mech, key, b"hello world")?;

// 【分割】同じ署名を、データを小分けにして渡す
session.sign_init(&mech, key)?;     // ① 開始（メカニズムと鍵をセット）
session.sign_update(b"hello ")?;    // ② データ前半を投入
session.sign_update(b"world")?;     // ②' データ後半を投入（何回でもOK）
let sig = session.sign_final()?;    // ③ 締めて署名を受け取る

    ops/stream.rs ではわざと 16 バイトずつに区切って、この仕組みを見せている。 迷ったら一発でよい。「分割」は “巨大データをメモリに全部載せずに処理したい” ときの上級テク。

    cryptoki の引数の読み方

    処理系メソッドの引数は、だいたい 「①手順」「②鍵」「③データ」 の3点セット。「金庫の窓口に出す注文書」と同じ構成。

    メソッド①手順②鍵③データ戻り値
    session.sign(&mech, key, data)&mech秘密鍵ハンドル署名対象署名 Vec<u8>
    session.verify(&mech, key, data, sig)&mech公開鍵ハンドル元データ()（OK/NG）
    session.encrypt(&mech, key, data)&mech鍵ハンドル平文暗号文 Vec<u8>
    session.decrypt(&mech, key, data)&mech鍵ハンドル暗号文平文 Vec<u8>
    session.digest(&mech, data)&mech（鍵不要）対象ハッシュ Vec<u8>

    ②の key は鍵の実体ではなく「ハンドル(整理番号)」。これが「秘密鍵は金庫から出さず、番号で指定して処理だけ頼む」という HSM の核心。 & は Rust の「借用」の印で、PKCS#11 の意味とは無関係。

    K. PKCS#11 3.0／3.2 で追加された関数

    ここまでの A〜J は 2.40 の 68 関数。v3.0 以降では インターフェース取得・複数ユーザ・メッセージベース暗号(AEAD)・耐量子の鍵カプセル化・新しい検証系が加わった。 本プログラムが使う cryptoki 0.10 はこれらの安全ラッパーをほぼ持たない（生 FFI / 新しめのバインディングが必要）。「最新仕様には何があるか」を把握するための一覧。

    K-1. インターフェース・全体（3.0）
    関数説明対応状況
    C_GetInterfaceListライブラリが提供するインターフェース一覧を取得✕
    C_GetInterface名前/版でインターフェースを取得。v3.0 以降の推奨エントリポイント（C_GetFunctionList の後継。3.x の新関数はこちら経由で得る）✕
    K-2. セッション・認証（3.0）
    関数説明対応状況
    C_LoginUserユーザ名付きログイン。複数ユーザ／3.0 の細かい認証モデルに対応✕

    K-3. メッセージベース暗号 / 復号（3.0・主に AEAD 向け）

    1 回の ...Init で、IV/AAD を都度変えながら複数メッセージを処理できる。GCM などで「メッセージごとに Init し直す無駄」を省くための系統。

    C_MessageEncryptFinalメッセージ暗号化の終了
    C_MessageDecryptInit / C_DecryptMessageメッセージ復号の開始 / 一発復号
    C_DecryptMessageBegin / C_DecryptMessageNextメッセージ復号の分割（開始 / 投入・締め）
    C_MessageDecryptFinalメッセージ復号の終了

    K-6. 署名検証の新系統（3.2）

    従来の C_Verify は「データ＋署名」を渡して OK/NG を得る。3.2 では 署名値を先にセットしてからデータを流し込む新しい検証系が追加された（ストリーミング検証に向く）。

    関数説明
    C_VerifySignatureInit検証開始（メカニズム＋公開鍵＋検証する署名値）
    C_VerifySignature一発でデータを渡して検証
    C_VerifySignatureUpdate / C_VerifySignatureFinal分割でデータを投入 / 締めて検証結果を得る
