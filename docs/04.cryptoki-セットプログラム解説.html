    1 · 概念

    1まず概念（金庫のたとえ）

    概念たとえ意味
    Library(.so)業務マニュアルlibsofthsm2.so。これをロードして全関数を得る
    Slot金庫の差込口接続点。スロット番号で指定
    Token金庫本体鍵やデータの実体。HSM 本体
    Session面談中の状態Token と会話する接続。開く→使う→閉じる
    Login暗証番号で本人確認PIN を入れる。秘密鍵操作にはほぼ必須
    Object金庫の中身鍵・証明書・データ。各々に Handle(整理番号)が付く
    Attribute中身に貼るラベルSign=true, Extractable=false など
    Mechanism作業手順RsaPkcs, Ecdsa, AesCbcPad などアルゴリズム指定
    最重要原則

    秘密鍵は金庫から出ない。アプリは「これに署名して」と注文書(Mechanism + データ + 鍵Handle)を渡し、結果だけ受け取る。

    04
    2 · 骨格

    2会話の骨格と 3 段ロケット

    外枠（ライフサイクル）

    lifecycle
    connect()      … C_GetFunctionList + C_Initialize
  pick_slot()    … C_GetSlotList
    login_rw()     … C_OpenSession + C_Login
      ── 本番処理 ──
    (自動)         … C_Logout / C_CloseSession  ← Session の Drop で自動
  (自動)         … C_Finalize                   ← Pkcs11 の Drop で自動

    cryptoki は終了処理(Finalize/CloseSession/Logout)を Drop で自動化するので、自分で書くのは「接続〜ログイン〜本番処理」だけ。

    Drop で後始末が自動になる仕組み（RAII）

    Rust では値がスコープを抜けると Drop が呼ばれる。cryptoki は Session の Drop で C_Logout＋C_CloseSession、Pkcs11 の Drop で C_Finalize を自動で呼ぶ。 生 FFI(doc 03)では閉じ忘れ・二重解放が起きやすかったが、ここでは「開いたら閉じる」を型とスコープが保証してくれる。だから本体コードは下のように短くなる。

    実際のコードの骨格（最小例）

    rust
    // ① 接続：.so をロードして初期化
let pkcs11 = Pkcs11::new(lib_path)?;
pkcs11.initialize(CInitializeArgs::OsThreads)?;

// ② スロットを選んで RW セッションを開く
let slot = pkcs11.get_slots_with_token()?[0];
let session = pkcs11.open_rw_session(slot)?;

// ③ ログイン（PIN）
session.login(UserType::User, Some(&pin))?;

// ④ 本番処理：鍵を探して署名する
let key = find_key(&session, "mykey")?;
let sig = session.sign(&Mechanism::Sha256RsaPkcs, key, data)?;

// ⑤ 後始末は書かない —— session と pkcs11 が
//    スコープを抜けるときに Drop が自動でやる

    骨格はこの 5 ステップだけ。session.rs が①〜③、ops/*.rs が④を担当する。? は「エラーなら即座に返す」演算子で、C の if (rv != CKR_OK) を毎回書く手間がなくなる。

    中身（3 段ロケット）

    PKCS#11 の処理系は Init → 本体 → (Final) で統一。cryptoki は前 2 段を 1 メソッドに合体する。

    操作C APIcryptoki
    署名C_SignInit + C_Signsession.sign(...)
    検証C_VerifyInit + C_Verifysession.verify(...)
    暗号化C_EncryptInit + C_Encryptsession.encrypt(...)
    復号C_DecryptInit + C_Decryptsession.decrypt(...)
    検索C_FindObjectsInit + Find + Finalsession.find_objects(...)
    05
    3 · 対応表

    3C API ↔ cryptoki 対応表

    生 FFI で何行も書いていた C API が、cryptoki ではどのメソッド 1 本に対応するかの対照表。「C でこう書く ＝ Rust でこう」を 1 対 1 で引けるようにしてある。

    cryptoki が肩代わりしてくれる 3 つのこと

    ① 関数表の取得：C_GetFunctionList は Pkcs11::new() の内部で自動。 ② 後始末：Finalize/CloseSession/Logout は Drop で自動。 ③ 型とエラー：属性やメカニズムは enum、戻り値は Result になり、CK_RV の数値判定や byte 詰めが要らなくなる。

    C APIcryptoki隠され方
    C_GetFunctionList+C_InitializePkcs11::new() + .initialize(CInitializeArgs::OsThreads)関数表取得は内部で自動
    C_FinalizePkcs11 の Drop書かなくてよい
    C_GetInfopkcs11.get_library_info()バージョン/提供元
    C_GetSlotListpkcs11.get_slots_with_token()Vec<Slot>
    C_GetSlotInfo/C_GetTokenInfoget_slot_info() / get_token_info()構造体で返る
    C_GetMechanismListpkcs11.get_mechanism_list(slot)対応アルゴリズム一覧
    C_OpenSessionpkcs11.open_rw_session(slot)RO/RW をメソッド名で表現
    C_Login/C_Logoutsession.login(UserType::User, Some(&pin)) / Dropユーザ種別が enum
    C_GenerateKeyPairsession.generate_key_pair(&mech, &pub_t, &priv_t)属性が Vec<Attribute>
    C_GenerateKeysession.generate_key(&mech, &t)対称鍵用
    CK_RV(0=OK)Result<T, Error>0 判定が ? に
    CK_ATTRIBUTEAttribute::Sign(true) などの enumbyte 詰め不要・型安全
    CK_MECHANISMMechanism::RsaPkcsKeyPairGen などの enum同上
    06
    3 · 対応表

    補足：CInitializeArgs と「4種のバージョン」

    CInitializeArgs の意味

    C_Initialize の引数は暗号と無関係で「マルチスレッド時のロック方法」だけを決める。 C 仕様では 4 モードあるが、cryptoki(0.10) は実用上の選択肢 OsThreads（= CKF_OS_LOCKING_OK、OS ネイティブロックでスレッドセーフ）を公開している。

    「バージョン」は 4 種類ある

    versions
    get_library_info() → cryptoki_version  // ① 仕様(API)の版  例 2.40 / 3.0 / 3.2
                   → library_version   // ② ライブラリ実装の版
get_slot_info()    → hardware_version  // ③ ハード版
                   → firmware_version  // ④ ファーム版

    ①の「仕様の版」は、トークンが実装する PKCS#11 の世代を示す。現行の最新仕様は v3.2（OASIS CS01, 2025-11-14）。SoftHSM2 など多くの実装は今も v2.40 相当を返す。

    4 · 構成

    4ファイル構成（どれが何をするか）

    src/ ├── lib.rs 共通の Result 型 + モジュール宣言 ├── session.rs 接続・スロット選択・ログイン・鍵検索（会話の骨格） ├── ops/ │ ├── mod.rs │ ├── info.rs 情報取得: バージョン/スロット/メカニズム/セッション │ ├── keygen.rs 鍵生成: RSA / EC / Ed25519 / X25519 / AES / HMAC │ ├── sign.rs 署名 / 検証（一発） │ ├── crypt.rs 暗号化 / 復号（一発） │ ├── digest.rs ハッシュ(SHA-256) │ ├── random.rs 乱数(C_GenerateRandom / C_SeedRandom) │ ├── objects.rs オブジェクト管理(list/attrs/destroy/copy) │ ├── keywrap.rs 鍵ラップ/アンラップ/ECDH 導出 │ ├── stream.rs 分割処理(Update/Final) │ └── admin.rs トークン/PIN 管理(init-token/init-pin/set-pin) └── bin/ └── hsm.rs CLI 本体（サブコマンドで上記を呼び分け）

    ほぼ全コマンドは cargo run --bin hsm -- help で一覧表示。 各関数の C API 対応は doc/05 関数リファレンス を参照。

    「署名したい → ops/sign.rs」「RSA 生成 → ops/keygen.rs::rsa」「取得系 → ops/info.rs」という対応で目的のコードにすぐ飛べる。

    4 · 構成

    鍵生成 3 種の比較（ops/keygen.rs）

    鍵関数メソッドMechanism鍵長/曲線の指定
    RSAkeygen::rsagenerate_key_pairRsaPkcsKeyPairGenModulusBits(2048) + PublicExponent
    ECkeygen::ecgenerate_key_pairEccKeyPairGenEcParams(OIDのDER)
    AESkeygen::aesgenerate_key(単数)AesKeyGenValueLen(32)

    非対称＝ペア生成(テンプレ2つ)、対称＝単数生成(テンプレ1つ)。詳細は doc/06 鍵生成の詳解。

    署名メカニズムの方針

    本プログラムの RSA 署名は Sha256RsaPkcs（PKCS#1 v1.5）を採用。SoftHSM 等での確実な動作と学習簡略化のためで、 新規設計では RsaPkcsPss（PSS, 現代の推奨）が望ましい点は doc/01 §10 の通り。

    5 · 使い方

    5使い方（準備 → 実行）

    準備（SoftHSM2 でトークン初期化）

    shell
    softhsm2-util --init-token --free --label "test" --so-pin 5678 --pin 1234
# .so を lib/ に置く（または環境変数 PKCS11_LIB で指定）

    実行

    shell
    # 取得系（ログイン不要・最初の疎通確認に最適）
cargo run --bin hsm -- info

# 鍵生成
cargo run --bin hsm -- gen-rsa 2048 mykey
cargo run --bin hsm -- gen-ec  p256 myec
cargo run --bin hsm -- gen-aes 32 myaes

# 署名 → 検証（sign が出す sig-hex を verify に渡す）
cargo run --bin hsm -- sign   mykey "hello hsm"
cargo run --bin hsm -- verify mykey "hello hsm" <sig-hex>

# 暗号化 → 復号
cargo run --bin hsm -- encrypt myaes "secret"
cargo run --bin hsm -- decrypt myaes <ct-hex>

    出力イメージ（info）

    出力例
    Cryptoki version : 2.40        # 仕様(API)の版
Library          : SoftHSM 2.6  # 実装の版と提供元
Slot 0  token "test"  present   # 使えるスロットとトークン
Mechanisms: RsaPkcsKeyPairGen, EcKeyPairGen, Sha256RsaPkcs, ...

    info はログイン不要なので、まずこれが通れば「.so が読めて、スロットとトークンが見えている」ことが確認できる。鍵生成や署名でつまずいたときも、最初に info へ戻ると切り分けが早い。

    5 · 使い方

    設定（環境変数）と実機への移行

    変数既定意味
    PKCS11_LIBlib/libsofthsm2.so.so のパス
    PKCS11_PIN1234ユーザ PIN
    PKCS11_SLOT0スロット index

    別の HSM へ移すときは、基本この 3 つ（パス・PIN・スロット）を変えるだけ。 PKCS#11 標準のおかげでコードはほぼそのまま動く（製品独自メカニズムの有無だけ注意）。

    softhsm2-util --init-token は初期化時にスロットが再採番されることがある。 info で実際のスロット番号を確認し、PKCS11_SLOT を合わせる。

    6 · 学習

    6学習ステップ（おすすめ順）

    • info（ログイン不要・3段ロケット無し。一番簡単）
    • gen-rsa → sign → verify（PKCS#11 の中核）
    • gen-aes → encrypt → decrypt
    • ops/*.rs を読んで C API 対応表(§3)と突き合わせる
    • 実機 HSM へ（.so/PIN/スロットの差し替えのみ）
