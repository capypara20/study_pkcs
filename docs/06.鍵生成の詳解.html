    0鍵生成で決めるのは「2つだけ」

    どのアルゴリズムでも、鍵生成で指定するのは次の 2 つだけ。

    • メカニズム(Mechanism) … どのアルゴリズムで作るか。例: RsaPkcsKeyPairGen, EccKeyPairGen, AesKeyGen
    • テンプレート(Template) … 作る鍵に貼る「属性(Attribute)の配列」。例: Token(true), Sign(true), Extractable(false)
    rust
    // 非対称(鍵ペア): メカニズム + 公開鍵テンプレ + 秘密鍵テンプレ
session.generate_key_pair(&mechanism, &pub_template, &priv_template)?;
// 対称(単一鍵):   メカニズム + テンプレ1つ
session.generate_key(&mechanism, &template)?;

    戻り値は 鍵の中身ではなくハンドル(整理番号)。秘密鍵は HSM から出てこない。

    呼び出しの流れ（シーケンス図）

    縦が時間、横線がやりとり。cryptoki が C API への変換を肩代わりする。

    1非対称(鍵ペア) と 対称(単一鍵)

    非対称鍵対称鍵
    例RSA, EC, Ed25519, X25519AES, 3DES, Generic-Secret
    鍵の数2つ(公開鍵+秘密鍵)がペア1つ
    メソッドgenerate_key_pairgenerate_key
    テンプレ2つ(pub用/priv用)1つ
    主な用途署名/検証, 鍵共有, 公開鍵暗号暗号化/復号, 鍵ラップ, HMAC
    長さ指定RSA=ModulusBits, EC=EcParams(曲線)ValueLen(バイト数)

    覚え方: 非対称=ペア生成=テンプレ2枚 / 対称=単数生成=テンプレ1枚。

    05
    2 · 属性

    2属性の意味（前半）— 保存場所・種別

    (a) 保存場所・識別

    Token(true)トークンに永続保存。falseならセッション限り(切断で消える)
    Label("...")人間が読む名札。検索(find_key)のキーに使う
    Id(...)バイト列の ID。証明書と鍵の紐付け等に使う

    (b) 鍵種別（対称鍵やラップ時に明示）

    Class(...)オブジェクト種別。PRIVATE_KEY/PUBLIC_KEY/SECRET_KEY
    KeyType(...)鍵アルゴリズム。RSA/EC/AES/GENERIC_SECRET 等

    generate_key_pair/generate_key では、メカニズムから種別が決まるので Class/KeyType を省略できることが多い（unwrap/derive 時は明示が要る）。

    06
    2 · 属性

    属性の意味（後半）— 能力・保護

    (c) 能力フラグ — 「その鍵で何ができるか」

    Sign(true)署名（秘密鍵/HMAC鍵）
    Verify(true)署名検証（公開鍵/HMAC鍵）
    Encrypt(true) / Decrypt(true)暗号化 / 復号
    Wrap(true) / Unwrap(true)他の鍵をラップ / ラップ鍵を取り込む
    Derive(true)鍵導出(ECDH等)に使える

    能力フラグは最小限だけ true にするのが鉄則(最小権限)。 署名専用の秘密鍵に Decrypt(true) は付けない。

    (d) 保護 — HSM の肝

    Private(true)このオブジェクトを見るにはログインが要る
    Sensitive(true)値(CKA_VALUE)を読み出せないようにする
    Extractable(false)鍵を(ラップしてでも)持ち出せないようにする

    Sensitive(true) + Extractable(false) が「鍵は金庫から出ない」を実現する組み合わせ。バックアップで持ち出したい鍵だけ Extractable(true)（→ wrap で取り出す）。

    07
    3 · アルゴリズム別

    3-1RSA（署名・暗号の定番）

    • メカニズム: RsaPkcsKeyPairGen
    • 長さ: ModulusBits(2048/3072/4096…) ＋ 公開指数 PublicExponent(=65537)
    • 後段: 署名は Sha256RsaPkcs(PKCS#1 v1.5) / 推奨は RsaPkcsPss、暗号は RsaPkcs/RsaPkcsOaep
    rust
    let pub_t = vec![
    Attribute::Token(true), Attribute::Verify(true), Attribute::Encrypt(true),
    Attribute::ModulusBits(2048.into()),
    Attribute::PublicExponent(vec![0x01,0x00,0x01]), // 65537
    Attribute::Label(b"my-rsa".to_vec()),
];
let priv_t = vec![
    Attribute::Token(true), Attribute::Private(true),
    Attribute::Sign(true), Attribute::Decrypt(true),
    Attribute::Sensitive(true), Attribute::Extractable(false),
    Attribute::Label(b"my-rsa".to_vec()),
];
session.generate_key_pair(&Mechanism::RsaPkcsKeyPairGen, &pub_t, &priv_t)?;

    CLI: gen-rsa 2048 my-rsa

    3 · アルゴリズム別

    3-2EC / ECDSA（短い鍵で強い。主流）

    • メカニズム: EccKeyPairGen
    • 長さの代わりに 曲線の OID を EcParams で渡す
    • 後段の署名: EcdsaSha256
    曲線名別名OIDDER(EcParams)
    p256prime256v1 / secp256r11.2.840.10045.3.1.706 08 2A 86 48 CE 3D 03 01 07
    p384secp384r11.3.132.0.3406 05 2B 81 04 00 22
    p521secp521r11.3.132.0.3506 05 2B 81 04 00 23
    secp256k1(Bitcoin等)1.3.132.0.1006 05 2B 81 04 00 0A

    CLI: gen-ec p256 my-ec / gen-ec secp256k1 btc（keygen::ec_curve_oid("p256") が上記 DER を返す）

    OID の DER って何?

    曲線名を表す数値列(OID)を ASN.1 でバイト列に符号化したもの。先頭 06 が「これは OID」、次が長さ、残りが中身。丸暗記不要、上表からコピーすればよい。

    3 · アルゴリズム別

    3-3/4Ed25519 と X25519

    Ed25519（最新の署名。高速・安全）

    • メカニズム: EccEdwardsKeyPairGen
    • EcParams = edwards25519 の OID(1.3.101.112) → 06 03 2B 65 70
    • 後段の署名: Eddsa（ハッシュ込みなので別途 SHA は不要）／ CLI: gen-ed25519 my-ed

    トークンによっては EcParams に OID でなく曲線名文字列 "edwards25519" を要求する実装もある。エラーが出たら名前文字列を試す。

    X25519（署名ではなく「鍵共有」用）

    • メカニズム: EccMontgomeryKeyPairGen
    • EcParams = curve25519 の OID(1.3.101.110) → 06 03 2B 65 6E
    • 能力は Sign ではなく Derive(true)（ECDH で共有鍵を作る）／ 後段: derive(ECDH)。CLI: gen-x25519 my-x

    3 · アルゴリズム別

    3-5/6AES と Generic-Secret(HMAC)

    AES（対称鍵。暗号化・鍵ラップ）

    • メカニズム: AesKeyGen、長さは ValueLen(バイト): 16/24/32 = AES-128/192/256
    • 後段: 暗号は AesCbcPad/AesGcm、鍵ラップは AesKeyWrapPad
    rust
    let t = vec![Attribute::Token(true), Attribute::ValueLen(32.into()),
             Attribute::Encrypt(true), Attribute::Decrypt(true),
             Attribute::Wrap(true), Attribute::Unwrap(true),
             Attribute::Label(b"my-aes".to_vec())];
session.generate_key(&Mechanism::AesKeyGen, &t)?; // ← 単数生成

    CLI: gen-aes 32 my-aes

    Generic-Secret（HMAC 用のただのバイト列鍵）

    • メカニズム: GenericSecretKeyGen、長さ ValueLen
    • Sign/Verify を true（HMAC の生成・検証に使う）／ CLI: gen-hmac 32 my-hmac

    4 · ゴール

    4「鍵 → 署名」の対応（ここがゴール）

    鍵の種類によって署名メカニズムが変わる。本プログラムの sign は 鍵の KeyType を読んで自動で選ぶので、利用者は鍵ラベルを渡すだけでよい（src/ops/sign.rs）。

    鍵生成KeyType署名メカニズム検証メカニズム
    gen-rsaRSASha256RsaPkcs同左
    gen-ecECEcdsaSha256同左
    gen-ed25519EC_EDWARDSEddsa同左
    gen-aes / gen-hmac(対称)署名ではなく暗号/HMAC—
    gen-x25519EC_MONTGOMERY署名不可(鍵共有専用)—
    shell
    cargo run --bin hsm -- gen-rsa 2048 rsakey
cargo run --bin hsm -- sign   rsakey "hello"      # → sig(hex)
cargo run --bin hsm -- verify rsakey "hello" <hex>
cargo run --bin hsm -- gen-ec p256 eckey && cargo run --bin hsm -- sign eckey "hello"
cargo run --bin hsm -- list      # 確認
cargo run --bin hsm -- attrs eckey

    5 · 注意

    5つまずきポイント

    • 鍵長/曲線の指定場所が違う: RSA=ModulusBits、EC=EcParams、対称=ValueLen。
    • 能力フラグ不足でエラー: 署名鍵に Sign(true) が無い、ラップ元に Extractable(true) が無い等。操作が CKR_KEY_FUNCTION_NOT_PERMITTED 等で弾かれたら、まず属性を疑う。
    • トークンが対応していない: info の対応メカニズム一覧に目的の *KeyPairGen が無ければ作れない（実機 HSM で要確認）。
    • Token(true) を忘れる: セッションが切れると鍵が消える。永続化したいなら必須。
