PKCS#11 STUDY SERIES · 04 — REFERENCE

メカニズム層リファレンス — “生”を埋める鍵生成機構の引き表

鍵生成メカニズム（CKM_*）を並べ、09 属性階層リファレンスの 生（トークンが生成）属性がどの機構で埋まるかを接続する引き表。あわせて SoftHSM2 / rust-cryptoki 安全層での「いま叩けるか」を付す。OASIS PKCS#11 v3.1 / v3.2 spec 準拠。

⚠ 読む前の注意 — これは「鍵生成メカニズム」だけの表

PKCS#11 のメカニズムは鍵生成のほかに 暗号化・署名・導出・ラップ など多数あるが、この表は C_GenerateKey / C_GenerateKeyPair に渡す生成系機構のみを扱う。09 のツリーが「属性を探す場所の地図」だったのに対し、10 は「その属性に値を書き込む主体（呼出側テンプレートか、機構か）の地図」。可否列はソースコード確認ベースであり、実行時の C_GetMechanismList はビルドオプションと crypto バックエンドに依存して変わる。

書呼出側がテンプレートで指定 黙省略可（機構が既定を補う） 生機構がトークン側で生成・寄与 読読取専用・トークン付与 ✓あり △条件つき ✗なし

「いま叩ける」＝ apt 版 SoftHSM2 (2.6.x) にあり、かつ本リポジトリ採用の cryptoki 0.10 安全層に enum がある行。09 の 粘（粘着性）は生成後のライフサイクルの話なので本表には登場しない。

背骨① — 「強度の指定方法」は6系統に分かれる

09 の 生 リーフ（MODULUS / EC_POINT / VALUE …）と機構をつなぐ軸は、呼出側が鍵の強度・サイズを何で伝えるか。全生成機構は次の6系統のどれかに落ちる。

① ビット数 — CKA_MODULUS_BITS

RSA 専用。公開鍵テンプレートに 2048 等を書く。私鍵側に書くのは 09 の罠①

② 曲線 — CKA_EC_PARAMS

EC / Edwards / Montgomery。DER 符号化の曲線OID（または curveName）。数値でなく「どの曲線か」で強度が決まる

③ バイト長 — CKA_VALUE_LEN

AES / GENERIC_SECRET。可変長の共通鍵はこれが必須。AES は 16/24/32 のみ

④ 固定長 — 指定なし

DES / DES2 / DES3。長さがアルゴリズム定義で 8/16/24 バイトに固定。VALUE_LEN を書かない（要求するのは AES/CAST 等の可変長側）

⑤ ドメインパラメタ — PRIME 等

DH（PRIME, BASE）/ DSA（PRIME, SUBPRIME, BASE）。群そのものをテンプレートに書き込む。素数長＝強度

⑥ パラメタセット — CKA_PARAMETER_SET

ML-KEM / ML-DSA / SLH-DSA（v3.2 追加）。FIPS 203/204/205 が定めた離散メニューから1つ選ぶ。数値指定の自由度は無い

背骨② — 非対称ギャップ：族ごとに「どちらのライブラリで叩くか」が決まる

可否2列を突き合わせると、仕様には揃っているのに実装側で互い違いに欠ける構図が見える。

古典側の欠け（DH / DSA）：spec にも SoftHSM2（apt 2.6.x）にもあるが、rust-cryptoki 安全層には Mechanism enum の variant がどのリリースにも無い（0.10 / 0.11 / 0.12 / main を確認）。叩くには cryptoki-sys の生 FFI か libloading 直叩きが必須。

PQC 側の欠け（ML-KEM / ML-DSA / SLH-DSA）：cryptoki 安全層は 0.11.0 で3機構とも揃えたが、SoftHSM2 は ML 系が develop ブランチのソースビルド限定（apt 2.6.x に無し）、SLH-DSA に至っては develop にも実装が無い。さらに本リポジトリは cryptoki = "0.10" 固定なので、PQC を書くにはまずクレート更新が要る。

つまり「cryptoki（安全層）＋ libloading（生FFI）」の二刀流は好みの問題ではなく、DH/DSA をやるなら生FFI しか無く、PQC をやるなら安全層（0.11+）しか無いという消去法で決まる。本プロジェクトの構成（src/main.rs=生FFI ／ src/bin/hsm.rs=cryptoki）はこのギャップにそのまま対応している。

09 との接続 — “生”リーフの出どころ対応

09 のツリーで 生 が付いたリーフは、この表の機構が埋める：RSA 公開鍵の MODULUS・私鍵の PRIVATE_EXPONENT 以下 CRT 成分 → ①、EC の EC_POINT／VALUE → ②、AES の VALUE → ③。逆方向に見ると、09 の属性ツリーに未掲載の鍵型が本表から浮かび上がる — 古典系では CKK_DH（PRIME / BASE / VALUE / VALUE_BITS）と CKK_DSA（PRIME / SUBPRIME / BASE / VALUE）の2型のみ（EC は 09 に既出、DES は CKA_VALUE 以外の型固有属性を持たない）。加えて v3.2 の PQC 3型（PARAMETER_SET / SEED / VALUE）も 09 のスコープ外。09 を増補するならこの5型が候補になる。

  • 一次確認済み：各機構の「テンプレートで指定する属性」「contributes（寄与）する属性」の全行は OASIS 仕様の原文（機構ごとの節）と突き合わせた。RSA の PUBLIC_EXPONENT 既定 0x10001（不可なら別値可）、DH の VALUE_BITS 補完、ML 系私鍵への CKA_SEED 寄与、SLH-DSA に SEED が無いこと、PARAMETER_SET 定数の全名称（ML-KEM 512/768/1024・ML-DSA 44/65/87・SLH-DSA 12種）、CKA_PARAMETER_SET / CKK_ML_* が v3.1 ヘッダに無く v3.2 ヘッダにあることも原文・公式ヘッダで確認。実装可否は rust-cryptoki（タグ 0.10.0/0.11.0/0.12.0 と main の Mechanism enum）、SoftHSMv2（タグ 2.6.1 と develop の SoftHSM.cpp / configure）のソースで確認した。
  • 確認手段の注記：docs.oasis-open.org が本セッションから到達不能だったため、仕様原文は OASIS TC の公式 GitHub リポジトリ（oasis-tcs/pkcs11）の spec ソース（現行ワーキング版 Markdown）＋公式公開ヘッダ（published/3-01, 3-02）で検証した。公開版 HTML との節番号の照合は行っていない。また本セッション環境に SoftHSM2 が無く、実機での C_GetMechanismList 実行確認は行っていない（可否列はソース確認ベース）。
  • 下書きからの訂正3点：(1) SLH-DSA は SoftHSMv2 に develop 含め未実装（「要ソースビルド」ですらない）。(2) CKM_EC_MONTGOMERY_KEY_PAIR_GEN も SoftHSMv2 未実装 — X25519 は Edwards 機構＋curveName という規格外流儀で代替。(3) cryptoki 安全層の PQC 対応は 0.11.0 からで、本リポジトリの 0.10 には無い。また configure フラグの既定は「on」ではなく detect（バックエンド検出）。
  • 独自整理：「強度指定6系統」の分類軸と、機構→09 の“生”リーフの対応付けはこちらで構成した整理。DES3_KEY_GEN の寄与は専用節が spec に無いため DES2 節と DES3 属性表（VALUE 固定 24B）からの類推。GENERIC_SECRET_KEY_GEN は spec に contributes の明示列挙が無く、VALUE 寄与は動作からの推定。
  • スコープ外：導出（CKM_*_DERIVE / HKDF / KBKDF）、ラップ、ドメインパラメタ生成（CKM_DSA/DH_PKCS_PARAMETER_GEN）、GOST、SHA*_KEY_GEN、HSS/XMSS。ベンダー差（鍵長上限、既定値、PQC の中身の実装品質）は本番 HSM で必ず再確認のこと。
