    PART I — 概念

    03HSMとは何か

    HSM（Hardware Security Module）は、鍵を保管し、暗号処理を「中で」実行する専用ハードウェア。アプリには鍵を渡さず、処理だけを請け負う。

    何をしてくれる？
    • 鍵の生成・保管
    • 署名・検証
    • 暗号化・復号
    • 乱数生成
    • 鍵のラップ（暗号化して持ち出し）
    絶対にしないこと
    • 秘密鍵を外に出すこと
      （属性で許可した場合の例外を除く）
    • アプリのメモリに鍵を載せること
    • 認証なしで秘密操作をすること

    PART I — 概念

    04PKCS#11とは何か

    暗号デバイス（HSM、スマートカード等）を操作するためのC言語API標準仕様。OASIS PKCS 11 TCが管理。別名 Cryptoki。最新は v3.2（OASIS Committee Specification 01, 2025-11-14）。

    ▸たとえると「統一注文書フォーマット」

    HSM の製品はメーカーごとに多数あって中身はバラバラ。でも 外向けの注文書だけは同じ書式で受け付けようや という業界合意。

    SuicaとICOCAとPASMOの関係に似てる。中身は違うけど、レジでの読み取り操作は同じ。

    アプリ開発者にとっての意味

    HSM 提供元の .so（Linux）や .dll（Windows）を ロードして、決まった関数を呼ぶ。HSM 製品を変えてもアプリ側のロジックは（基本的に）動く。※ 実際は製品ごとの方言あり

    出典：[1] PKCS#11 Spec v3.2[5] OASIS PKCS 11 TC

    PART II — 5つの基本概念

    06Slot と Token

    Slot = 棚の番号、Token = その棚に置いてある実際の箱。1台のHSMを複数チームで分割使用するときの単位にもなる。

    Slot（スロット）

    棚の番号。実機HSMでは「パーティション」と呼ばれることが多い。物がなくても番号は存在する。

    関数：C_GetSlotList / C_GetSlotInfo

    Token（トークン）

    その棚に置いてある実際の箱。鍵やデータが入る器。ラベル名、製造元、対応Mechanism等のメタ情報を持つ。

    関数：C_GetTokenInfo

    出典：[1] PKCS#11 Spec v3.2 §5
    07 / 19
    PART II — 5つの基本概念

    07Session

    セッション = アプリとTokenの間の論理接続。電話と同じ感覚で、開いて、用件を済ませて、閉じる。

    ⚠マルチスレッドの大原則

    1セッションを複数スレッドで共有しない。途中で別スレッドの操作が入ると、セッションの「今、何の操作中か」がぐちゃぐちゃになる。

    スレッドごとに別のC_OpenSessionを持つのがルール。

    出典：[1] PKCS#11 Spec v3.2 §5.6 Session
    08 / 19
    PART II — 5つの基本概念 (★ 最重要)

    08Object と Handle

    HSMの本質はここ。鍵そのものはアプリに出てこない。代わりに整理番号（Handle）を受け取って、「47番でお願いします」と頼む。

    ▸普通のソフトウェア暗号

    key = "ABCDEF123456..."
       ↑ 鍵そのものがメモリに乗る
sign(key, data)
       ↑ 流出リスク

    ▸HSM経由

    key_handle = 47
       ↑ ただの整数（預かり証）
sign(key_handle, data)
       ↑ 鍵はHSM内で完結
    なぜハンドル方式？

    PCがマルウェアに感染しても、メモリには整数しかないから鍵自体は盗まれない。これがHSMを使う最大の理由。

    PART II — 5つの基本概念

    09Attribute（属性）

    Object（鍵・証明書・データ）はすべて属性（タグ）の集合として表現される。鍵を作るときも検索するときも、属性で指定する。

    ▸主な属性の意味

    CKA_CLASS
    オブジェクトの種類（秘密鍵・公開鍵・証明書等）
    CKA_KEY_TYPE
    鍵のアルゴリズム（RSA / EC / AES）
    CKA_LABEL
    ユーザー定義の名前。検索に使う
    CKA_SIGN / CKA_VERIFY
    用途フラグ（署名OK・検証OK等）
    CKA_SENSITIVE
    秘密値の保護フラグ
    CKA_EXTRACTABLE
    外部に持ち出し可能か（要注意）
    CKA_TOKEN
    永続オブジェクト（true）／揮発（false）
    設計上のキーポイント

    CKA_EXTRACTABLE を true にすると、鍵を暗号化して外に出せる。用途次第やけど、本番運用では基本 false。一度falseにしたら原則戻せない（製品差あり）。

    出典：[1] PKCS#11 Spec v3.2 §10 Object types
    10 / 19
    PART II — 5つの基本概念

    10Mechanism（メカニズム）

    暗号操作の「種類」「方式」を指定する仕様。鍵とメカニズムは別物。料理でいうと「材料」と「レシピ」の関係。

    ▸同じRSA鍵でも色んな使い方

    CKM_RSA_PKCS
    古いパディング方式（PKCS#1 v1.5）
    CKM_RSA_PKCS_PSS
    PSSパディング（現代の推奨）
    CKM_RSA_PKCS_OAEP
    暗号化用パディング
    CKM_SHA256_RSA_PKCS
    ハッシュ込みのコンビ品

    ▸カテゴリ別の代表

    RSA系
    CKM_RSA_PKCS_PSS, CKM_RSA_PKCS_OAEP
    EC系
    CKM_ECDSA_SHA256, CKM_ECDH1_DERIVE
    AES系
    CKM_AES_CBC_PAD, CKM_AES_GCM
    ハッシュ
    CKM_SHA256, CKM_SHA512
    鍵生成
    CKM_RSA_PKCS_KEY_PAIR_GEN
    注文書のイメージ

    「鍵 = #47」「メカニズム = RSA-PSS」「データ = ファイルの中身」
    この3点セットを毎回 C_SignInit + C_Sign で渡す。

    ⚠製品差の罠

    仕様書に載ってるMechanismでも、HSMが対応してない場合がある。最新のEdDSAとか、PSSの細かいパラメータとか。事前に C_GetMechanismList で対応一覧を取って確認する。

    出典：[1] PKCS#11 Spec v3.2 §6 Mechanisms

    PART III — ライブラリの内側

    11ライブラリ内部の4つの役割

    「窓口係」と一言で呼んできたけど、実際は4つの仕事を兼ねてる。処理の流れと時間のかかり方を理解するにはこの分担を意識する。

    ① 受付係 / ② 帳簿係

    標準APIの窓口と内部状態の管理。マルチスレッドでのスケールはここの設計次第で決まる。

    ③ 翻訳係 / ④ 配達係

    ネットワーク型HSMでは④の通信往復にかかる時間が大半を占めることが多い。TLS接続は使い回しが必須。

    12 / 19
    PART III — ライブラリの内側

    12実装パターン4種

    同じPKCS#11ライブラリでも、HSMとの接続手段によって時間のかかり方がガラッと変わる。

    A — ソフトウェアHSM (★この資料で使う)

    ソフトウェアだけで PKCS#11 を実装したもの

    アプリ → .so → ローカルファイル

    用途: 開発・学習・API動作確認

    ハード不要で手元に入れられる。処理時間は CPU 次第。

    B — ネットワーク型HSM

    ネットワーク先のアプライアンスに接続

    アプリ → .so → TLS → アプライアンス

    特徴: 1リクエストごとにネットワーク往復

    往復にかかる時間が大きい。コネクション使い回しが効く。

    C — PCIeカード型

    サーバに挿す拡張カード

    アプリ → .so → ドライバ → PCIeバス

    特徴: 往復が短く応答が速い

    1台のサーバに数枚しか挿せない

    D — USBトークン型

    USB 接続の小型デバイス・スマートカード

    アプリ → .so → libusb / PC/SC

    特徴: 個人/小規模向け、低コスト

    USB通信ぶんの時間が乗る

    時間がどこにかかるか
    パターン主に時間がかかる所備考
    A (ソフト)CPU・暗号演算SoftHSM。手元で API の動きと処理時間を確かめられる
    B (ネット)ネットワーク往復往復が支配的、並列化で稼ぐ
    C (PCIe)HSM内部演算往復が短く演算そのものが見えやすい
    D (USB)USB通信シリアル通信に近い特性
    出典：[6] SoftHSM2[1] PKCS#11 Spec v3.2

    PART IV — 関数と処理フロー

    13関数の命名規則

    PKCS#11の関数は すべて C_ で始まる。名前自体が役割を語るように設計されてる。

    ▸動作の例

    • Open / Close — 開く / 閉じる
    • Get / Set — 取得 / 設定
    • Find — 検索
    • Generate — 生成
    • Sign / Verify — 署名 / 検証
    • Encrypt / Decrypt — 暗号化 / 復号
    • Wrap / Unwrap — 鍵のラップ

    ▸対象の例

    • Session — セッション
    • SlotList / SlotInfo — スロット
    • TokenInfo — トークン情報
    • Object / Objects — オブジェクト
    • Key / KeyPair — 鍵
    • AttributeValue — 属性値
    • Random — 乱数

    英語が読めれば関数名から動作を推測できる。これがPKCS#11の親切なところ。一度パターンを覚えたら、HSM 製品が変わっても同じ関数名で書ける。

    PART IV — 関数と処理フロー

    14機能カテゴリマップ

    PKCS#11の全関数は大きく7グループに分類できる。実際に手を動かすとき主に叩くのは⑥。

    カテゴリ代表的な関数役割
    ① 全体管理 C_Initialize / C_Finalize / C_GetFunctionList ライブラリの起動と終了
    ② Slot/Token情報 C_GetSlotList / C_GetTokenInfo / C_GetMechanismList 環境情報の取得
    ③ セッション C_OpenSession / C_CloseSession / C_Login / C_Logout 接続と認証
    ④ オブジェクト C_FindObjects... / C_GetAttributeValue / C_CreateObject 鍵や証明書の検索・属性操作
    ⑤ 鍵管理 C_GenerateKey / C_GenerateKeyPair / C_WrapKey / C_UnwrapKey 鍵の生成・ラップ
    ⑥ 暗号操作 C_Sign... / C_Verify... / C_Encrypt... / C_Decrypt... / C_Digest... / C_GenerateRandom ★ 実際に動かして時間を見る主対象
    ⑦ その他 C_SeedRandom / C_WaitForSlotEvent 付加機能
    処理時間を見るときの分け方

    ①〜⑤は準備フェーズ。⑥を繰り返し叩く部分が本処理フェーズ。これをはっきり分けておくと、SoftHSM で時間を測ったときの結果が読み取りやすい。

    出典：[1] PKCS#11 Spec v3.2 §5 Function categories

    PART IV — 関数と処理フロー

    153段ロケット構造

    PKCS#11の最大のクセ。データを処理する操作はだいたい3段階に分かれる。

    ▸操作別のセット

    操作Init（準備）本処理Final（分割時）
    署名C_SignInitC_SignC_SignFinal
    検証C_VerifyInitC_VerifyC_VerifyFinal
    暗号化C_EncryptInitC_EncryptC_EncryptFinal
    復号C_DecryptInitC_DecryptC_DecryptFinal
    ハッシュC_DigestInitC_DigestC_DigestFinal
    検索C_FindObjectsInitC_FindObjectsC_FindObjectsFinal
    なぜ3段？

    セッションが「今、何の操作中か」を覚えてる必要があるから。C_Sign単独では呼べない。先にC_SignInitで「これからどの鍵で、どのMechanismで」を宣言しておく。

    単発で完結する操作

    C_GenerateKey、C_GenerateRandom、C_GetAttributeValue、C_WrapKey などは単発。「データを処理する系」だけ3段と覚える。

    出典：[1] PKCS#11 Spec v3.2 §5.13-5.18

    🏦 「営業終了」

    PART V — SoftHSMで動かす

    17処理時間の見方

    SoftHSM を入れれば、ハード無しで各操作にどれくらい時間がかかるか手元で確かめられる。準備と片付けは1回、本処理だけループして時間を見るのがコツ。

    準備
    時間を見る対象の外
    .soロード → C_GetFunctionList → C_Initialize → C_GetSlotList → C_OpenSession → C_Login → C_FindObjects...
    ↓
    ならし
    運転
    対象の外（初回だけ遅くなる分を外す）
    for i in 1..100: C_SignInit + C_Sign（空打ち）
    ↓
    ★ここを見る
    この区間の時間だけ見る
    for i in 1..N: t0 = now() → C_SignInit + C_Sign → t1 = now() → time[i] = t1 - t0
    ↓
    まとめ
    ざっくり見るだけでも十分
    平均・最小・最大・1秒あたりの回数
    ↓
    片付け
    C_Logout → C_CloseSession → C_Finalize
    よくあるズレの原因
    • ならし運転を忘れて初回の遅い分が混ざる
    • 戻り値チェック忘れでエラーの回も数えてしまう
    • C_Signを呼ぶ前にC_SignInitを忘れる
    • 鍵生成と署名を同じ枠で見る（極端に遅い値が混ざる）
    エラーハンドリング

    すべての関数はCK_RV型を返す。CKR_OK = 0 なら成功、それ以外はエラー。

    よく見る：CKR_SESSION_HANDLE_INVALID, CKR_USER_NOT_LOGGED_IN, CKR_MECHANISM_INVALID

    出典：[1] PKCS#11 Spec v3.2 §5.1 Return values[3] PKCS#11 Usage Guide v3.2
